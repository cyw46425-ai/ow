# RAG 设计与切片策略

## 为什么不用“整份文档一次塞给模型”

整文档输入成本高、噪声大，且当前活动与历史活动容易混淆。本项目把知识整理成面向用户问题的原子知识单元，每个单元都能独立支撑一个结论。

## 切片规则

当前知识库是人工结构化切片，而不是按固定字符数机械截断：

1. 一个切片只回答一个主要问题，例如“团灭后为什么要集合”或“怎么看英雄胜率”。
2. 每片包含 `id`、类别、标题、摘要、关键词、结论、原因、步骤、误区和外部链接。
3. 动态内容额外标记 `dynamic`、`asOf` 和版本状态；历史内容标记为 `historical`。
4. 召回给模型的单片最多 1,800 字符，Top K 默认 5，服务端再次限制为最多 6 片、每片 2,000 字符。
5. 英雄克制和地图推荐不切成自由文本，而是保留为结构化规则，避免生成模型改变关键决策。
6. 英雄技能采用“一名英雄一个切片”；跨英雄联动采用“一条机制一个切片”，防止把整套英雄资料塞进同一上下文。
7. 职业选手采用“一名选手一个切片”，社区梗采用“一组同义表达一个切片”；动态战队字段必须携带核验日期。

当前知识库由四层组成：基础玩法与资讯、53 个英雄技能切片、技能联动/社区文化扩展、职业选手与赛事档案。这样既能回答“安娜有什么技能”，也能区分“禁疗怎样和队友联动”与“职业比赛里谁擅长安娜”。

## 检索算法

本地检索不依赖第三方向量数据库：

- 中文按单字、二元组和三元组分词，英文与数字保留完整 token。
- BM25 负责精确词和稀有词匹配。
- 256 维哈希 TF-IDF 向量与余弦相似度负责相近词序和局部表达变化。
- 关键词短语、意图类别、官方来源和时效状态提供额外加权。
- 最终分数用于排序和界面诊断，不冒充概率或模型置信度。

这里的“向量”是可离线运行的词法 TF-IDF 向量，不是语义 Embedding。后续数据量超过数百切片后，可换成多语言 Embedding + 向量数据库，并保留 BM25 做混合检索。

## 上下文策略

前端只传最近 4 轮对话，并在每个新问题中重新分类和检索。上下文用于理解省略指代，不直接沿用上轮英雄实体；因此“怎么克制毛妹”之后再问“艾兴瓦尔德玩什么 T”，会以新问题中的地图和职责为主。

## 生成约束

Cloudflare Pages Function 把 Top K 证据发送给 DeepSeek，并要求：

- 只能基于给定证据回答具体数值、日期、赛果和版本改动。
- 资料不足时明确说明缺少什么。
- 输出固定 JSON：直接结论、依据、最多 4 条步骤、限制说明和使用的来源编号。
- `used_sources` 会在服务端与真实召回来源白名单比对，不能伪造来源编号。
- 模型失败、超时或 JSON 不合法时，回退到本地最高匹配知识单元。

## 评测

`npm run evaluate` 会验证意图分类准确率、Recall@3、Recall@5、MRR@5，以及每条失败用例的预期文档和实际排序。

当前黄金集属于回归测试，不代表线上泛化。生产版还应加入真实用户问题、无答案率、引用正确率、人工有用率、P95 延迟和单次回答成本。
